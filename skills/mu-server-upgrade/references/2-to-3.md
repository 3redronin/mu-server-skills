# Upgrade Mu Server 2.x to 3.x

Use the [Mu Server 3 release and migration notes](https://muserver.io/changelog/mu-server-3) as the source of truth for migration behavior. Treat Mu Server 3 as a released major version. A straightforward application with unambiguous routes and one explicitly registered JSON provider may need few source changes, but several defaults and specification-sensitive behaviors require focused tests.

## Required platform changes

- Raise the Java compiler and runtime minimum from 8 to 11.
- Move from Jakarta REST 3.0 to 3.1. Mu Server continues to supply its supported Jakarta REST API transitively.
- Move logging integration from SLF4J 1.7 to SLF4J 2.0. If the application supplies a binding, replace it with an SLF4J 2 provider; an SLF4J 1.7 binding is not discovered by SLF4J 2's service-provider mechanism.
- Account for JSpecify annotations on public Mu Server APIs. JVM descriptors remain compatible, but strict Java analysis and Kotlin can surface new nullness findings.
- Remove any use of the unused public `io.muserver.Toggles` class, which no longer exists.

The Maven coordinates and Java package names stay the same. Direct `MuServerBuilder` and `RestHandlerBuilder` setup remains valid; an upgrade does not require changing the application's architecture.

Keep explicitly registered resource and provider instances. For example, preserving the version 2 HTML fallback while retaining a JSON provider that implements both Jakarta REST contracts looks like this:

```java
RestHandlerBuilder api = RestHandlerBuilder.restHandler(resource)
    .addCustomReader(jsonProvider)
    .addCustomWriter(jsonProvider)
    .removeExceptionMapper(Throwable.class);
```

Mu Server has no generic `addProvider` method: register each provider through the method for the contract it implements.

Mu Server 3 implements the supported parts of Jakarta REST 3.1 and passes their applicable TCK tests. It still does not provide per-request resource construction, dependency injection, classpath scanning, or the Jakarta REST client. The Jakarta REST 3.1 `EntityPart` multipart API is not supported.

## Behavior most likely to affect applications

| Area | Version 2 | Version 3 | Upgrade action |
| --- | --- | --- | --- |
| Unhandled REST exceptions | Standard Mu Server HTML error response unless a mapper is registered. | A default `Throwable` mapper returns RFC 9457 `application/problem+json`; specific application mappers still win and a `WebApplicationException` with an entity keeps its response. | Decide whether to accept the new JSON contract, configure it, or call `removeExceptionMapper(Throwable.class)` for the HTML fallback. Test status, media type, headers, fields, and information disclosure. |
| Graceful shutdown result | `stop(...)` returns `false` after clean shutdown and `true` after timeout, contrary to its documented contract. | The result is corrected to `true` for clean shutdown and `false` for timeout. | Remove any compensation for the version 2 behavior and test both outcomes. |
| Providers | A built-in or wildcard provider can win; generic and runtime entity types can be lost. | Application providers win over built-ins; media specificity, runtime Java type, and generic type participate correctly. | Test custom JSON/XML readers and writers with overlapping types and media types. |
| Filters and interceptors | `@Priority` is not enforced; reader order can be the reverse of addition order. | Request filters and reader/writer interceptors use ascending priority; response filters use descending priority. `abortWith` stops the request chain and bypasses exception mapping. | Encode required order with distinct priorities and assert it externally. |
| Parameters and matching | Object arrays are unsupported; several inherited, empty, repeated-capture, and bodyless-request cases have implementation-specific results. | Object arrays are supported for non-path parameter annotations; matching and inheritance follow Jakarta REST 3.1 more closely. Invalid conversion uses the default problem response. | Keep working collections unless a change is useful. Test repeated, missing, empty, invalid, inherited, and bodyless cases the API exposes. |
| URI and `Location` handling | Form spaces, literal plus signs, encoded slashes, URI builders, and relative `Location` can use version 2 behavior. Given a request to `/app/items/123`, `Response.created(URI.create("next"))` produces `Location: /app/items/next`. | Component-specific encoding is corrected; relative `Location` resolves against the application base URI, so the same example produces `Location: /app/next`. This is base-relative resolution, not a guarantee that the header becomes a fully absolute URI. | Assert exact raw and decoded values, redirects, signatures, and `Location` headers where clients observe them. Return an explicit URI for the intended wire value rather than relying on either version's implicit base. |
| Responses and cookies | Default status derivation and session-cookie output can differ; Jakarta REST 3.1 `SameSite` is unavailable. | Entity responses default to `200`, empty responses to `204`; session cookies omit expiry attributes; `SameSite` is supported. | Set status explicitly when it is contractual and retest exact `Set-Cookie` output. |
| SSE lifecycle | Closed state, cascading close, and concurrent callbacks have known version 2 inconsistencies. | Closed state and broadcaster lifecycle are corrected; each concurrent callback is delivered at most once. | Test disconnect, close, broadcast, and shutdown races if the application uses SSE. |

Also test non-public annotated resource methods: both versions ignore them, while version 3 adds a startup warning. Fix the visibility rather than relying on the method being ignored.

## Optional version 3 APIs

`RestHandlerBuilder.fromApplication(application)` can adapt a Jakarta REST `Application`: resource and provider instances from `getSingletons()` remain singletons, and supported provider classes from `getClasses()` are constructed once through public no-argument constructors. Resource classes in `getClasses()` are rejected because Mu Server does not support their per-request lifecycle. Application properties, features, dynamic features, context resolvers, and scanning remain unsupported. An `@ApplicationPath` application must be started with `SeBootstrap`; direct `fromApplication` rejects it.

`SeBootstrap` is available when standard Jakarta REST Java SE bootstrap is itself useful. Select Mu explicitly first with `MuRuntimeDelegate.ensureSet()` or the standard runtime-delegate system property. Keep direct Mu Server bootstrap when it already fits the application.

## Focused verification

Start with the application's existing routes. Add targeted probes only for crossed behavior: default and custom errors, malformed headers or parameters, provider selection, filter/interceptor order, repeated parameters, bodyless `@Consumes` methods, exact URI and `Location` values, response defaults, cookies, SSE concurrency, and both graceful-shutdown outcomes. Test HTTP/2, TLS, uploads, WebSockets, or streaming only when the application uses them.
